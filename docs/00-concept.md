## 0. 要約

**製品の芯(提案):** 「鼻のケア・症状・生活要因を1分で記録し、効いたものと悪化要因の候補を絞り、受診用の記録を作り、治ったら消す」短期専用ツール。

**構成(要望):** ハミング機能は単体で完結させ、他の機能は必要になってから足す。

**原案から変えたい点(重要順)**

| # | 変更点 | 理由 |
|---|---|---|
| 1 | 「鼻のにおい」と左右差を、受診を促す判断材料として扱う | 片側症状や悪臭(cacosmia)は、より急いだ対応を検討する特徴とされる。悪臭を伴う片側の副鼻腔炎では歯が原因の場合もあり、洗浄やハミングでは解決しない可能性がある |
| 2 | 点鼻薬を種類で分け、血管収縮薬はストリークから除外する | 連用で悪化しうる薬を「継続」で褒めてしまう |
| 3 | M1はハミング単体とし、日々の記録はM2、環境と睡眠はM3以降に回す | ハミングが開発の動機で技術リスクも最大。天気は過去92日分を後から取得できた |
| 4 | 部位を選んで響く音を登録し、毎日の練習でその音をガイドする(要望) | 測れるのは音程で、振動は本人の体感。副鼻腔の共鳴や効果との一致は未確認 |
| 5 | 素朴な相関分析はやらない | 無関係なデータでも、回復中は高確率で「有意」になる(§7) |
| 6 | 花粉の自動取得は後回し | 今の時期に使える日本の花粉データがなく、短期利用では変動もない |
| 7 | 通知には小さなサーバーが必要と認める | PWAだけで定時通知を出す確実な手段がない |
| 8 | 出口(卒業条件)と受診サマリを追加する | 「治ったら削除」の判定基準がなく、記録の出口もない |

## 1. 目的の再定義

原案の「診断」は「自分の鼻の状態を把握する」と言い換える。アプリは病名を判定しない(HC-1)。

アプリが答える問いは次の6つに絞る。

| 問い | 答え方 |
|---|---|
| 今日のケアはやったか | チェックボックス |
| 良くなっているか | 総合スコアの推移と週1回の変化評価 |
| 何で悪化するか | 「候補」まで。断定しない |
| ハミングは自分に効くか | 前後比較と自己実験 |
| 受診すべきか | 危険サイン、期間の目安、受診サマリ |
| もう消してよいか | 卒業カウンター |

**成功条件(提案):** 毎日の記録が1分以内、症状が落ち着いたら迷わず削除できる、受診時に1枚の要約を出せる。

## 2. Hard Constraints と非目標(2026-11-04 承認)

| ID | 制約 | 担保の方法 |
|---|---|---|
| HC-1 | 病名を判定せず、医療効果をうたわない。出力は記録の要約と受診の目安のみ | 文言を定数に集約し、禁止語をテストで検出 |
| HC-2 | 薬の開始・中止・増減を提案しない。処方薬を自己実験の対象にしない | 実験の対象を許可リスト制にし、薬カテゴリーを拒否するテスト |
| HC-3 | 危険サインと中止条件は初回に全員へ1回表示し、以後は情報ページに常設する。能動的に案内するのは、該当する入力があったときだけ | 初回表示と情報ページへの導線のテスト |
| HC-4 | 血管収縮薬はストリークの対象外とし、連続使用日数を警告する | 集計関数のテスト |
| HC-5 | 健康データを端末の外に出さない。例外は丸めた位置情報と、通知抑制用の完了フラグのみ | 送信関数を1か所に集約し、送信内容をテスト |
| HC-6 | 音声は端末内で処理し、録音も送信もしない | 保存処理を実装せず、音声は数値へ変換して破棄 |
| HC-7 | 相関を因果として表示しない。データ不足時は理由コードで非表示にする | 表示判定を純粋関数にしてテスト |
| HC-8 | ハミング機能は他の機能、通知サーバー、外部API、アカウントなしで動く(要望) | 他モジュールへの依存を検査するテストと、ハミングのみ有効にした状態の通しテスト |

**デザイン原則(要望):** 余白を主役にする。1画面に1タスク。注意書きは初回に1回だけ出し、以後は目立たない場所に置く。説明は必要になったときに開く。

**ガードの実装状況:** HC-1〜8のすべてをテストで検査している。HC-5の例外(丸めた位置情報と完了フラグ)を使う機能はまだない。

**非目標:** 他者への配布、アカウント機能、クラウド同期、AIによる診断、写真判定、食事の全面記録、長期のライフログ、ネイティブアプリ化。公開先はGitHub Pagesなので、URLを知っていれば誰でも開けるが、自分用として広めない(D-019)。

配布する場合は、医療機器プログラムへの該当性、SNOT-22のライセンス、データ提供元の規約を改めて確認する。

## 3. 原案のレビュー

### R-1 臭いと後鼻漏は「客観的」ではない
どちらも自己申告で、主観的な指標である。客観寄りの指標は §5 の案(洗浄液の戻り、香りの識別など)で補う。

### R-2 「後鼻漏」の意味が衝突している
毎日の症状では後鼻漏は悪い指標だが、ハミング直後の後鼻漏は良い効果として記録する案になっている。同じ言葉のままでは、効いている日ほどスコアが悪く見える。

- 毎日の項目: **後鼻漏の不快感**(0〜10)
- ハミング直後の項目: **排出感**(なし/少し/はっきり)

「直後に流れる=良い効果」自体も仮説なので、「楽になったか」とは別に記録する。

### R-3 嗅覚とにおいの評価には罠がある
- **スケールの向き:** 嗅覚だけ高いほど良い項目になりかねない。「嗅覚低下」(0=正常、10=全くわからない)として向きを揃える。
- **見かけの改善:** 嗅覚が落ちると悪臭も感じにくくなる。におい単独の改善は回復とは限らないため、必ず2項目をセットで表示する。

### R-4 鼻のにおいと左右差の扱い(日々の記録を使う場合)
英国の紹介基準の一例では、鼻症状に片側性、出血、痂皮、悪臭が伴う場合、より急いだ対応を検討するとしている。片側の鼻閉と血性鼻汁は、がん疑いの緊急紹介ルートの対象とされている。歯が原因の副鼻腔炎では分泌物に悪臭を伴うことが多いとされ、片側の上顎洞炎に占める割合は最大75%という報告もある(ただし報告値にはばらつきが大きい)。

したがって、日々の記録では左右も残し、片側性や悪臭が続くときは受診の目安を表示する。

目安の文言は米国の総説(AAFP 2017)なども参考にする。同総説は、第一選択を鼻洗浄とステロイド点鼻とし、改善しなければ耳鼻科へ紹介し、診断の確定にはCTや内視鏡を用いると整理している。

### R-5 点鼻薬を1項目にできない
| 種類 | 扱い |
|---|---|
| ステロイド | 継続が前提なので、ストリークの対象。効果は当日の相関では測らない |
| 血管収縮薬 | 英国規制当局は5日までと制限。ストリーク対象外で、連続日数を警告 |
| その他 | 使用記録のみ |

点鼻薬は既定のルーチンには含めず、使い始めたときに種類を選んで追加する。

### R-6 ハミングの根拠は「機序はあるが効果は未確立」
| 分かっていること | 設計への反映 |
|---|---|
| 健常者10人で鼻腔NOが約15倍(Weitzberg 2002) | 仕組みの根拠。治療効果の根拠ではない |
| 連続するとNOのピークは段階的に低下し、3分の休止で回復(Maniscalco 2003) | 「短いセット+休憩」をプリセットにする |
| NOのピークを最も左右するのは副鼻腔の開口部の大きさで、周波数も影響する | 周波数の微調整より、鼻の通りを先に確保する順序を試す |
| 開口部が完全に閉塞した重度ポリープではピークが消失。アレルギー性鼻炎でも、ピークがない例は開口部の閉塞を示す内視鏡所見と関連 | 慢性化して通りが悪い状態では効果が出にくい可能性がある。無反応の日は「効かない」と断定せず、鼻の通りと併せて見る |
| 1時間×4日で改善の報告は**1例のみ**、約130Hz(Eby 2006) | 「連続型」として比較対象に入れるが、推奨はしない |
| ランダム化試験(60人、Abishek 2019)では、ステロイド点鼻と洗浄を含む標準治療にハミング呼吸法を1日2回足した群が12週時点で有意に良好。ただし差はSNOT-22で約3.4点(筆者計算)で、変化の目安8.9点より小さい。4週時点では有意差なし。**ハミング単独の試験ではない** | 効果は小さく遅い可能性がある。アプリ内の表現は「試している方法」とし、数日での判定を促さない |

### R-7 共鳴周波数の探索(部位登録方式)

**要望:** アプリが基準音を鳴らし、ユーザーがその音程でハミングして、震える周波数を探す。さらに、副鼻腔の位置を案内し、「ここを震わせられるのはこの周波数」とユーザーが登録して、毎日のルーティンでその音をガイドする。

**結論: 実現できる。** マイクで共鳴を自動検出するのではなく体感で判定するので、スマホの計測精度に依存しない。ただし、結果の意味は次のように区切る。

| 段階 | 内容 | 根拠 |
|---|---|---|
| 測れるもの | アプリが測るのは音程だけで、振動は本人の体感 | M0の実機検証、自分の体感 |
| 関係しそうなもの | 鼻腔全体の共鳴。鼻音の第1共鳴は約300Hz付近で、鼻腔と副鼻腔の形によって個人差が出る | Pruthi 2004(Fujimura を引用) |
| 未確認 | 副鼻腔そのものの共鳴との一致 | 副鼻腔由来の反共振は3人の測定で310〜1070Hz、個人差と左右差が大きい。単純な式は約41%過大に見積もった例があり、献体研究では開口部を開放して初めて明瞭な谷が現れた |
| 未確認 | 振動が最大の音程でNOや排出も最大になること | 周波数が影響するとの記載はあるが、周波数別の数値は入手できていない |

そこで結果は「額が響く音」のように体感の言葉で表し、効果は別に確かめる(§7の比較実験)。

低い声では倍音が共鳴帯に重なるので(例: 130Hzの第2倍音は260Hz)、**響く音が複数ある可能性がある**。これは筆者の推論で未検証のため、部位ごとに複数の音を登録できるようにする。

額は裏声でないと震えないのではないかという実感は、副鼻腔由来の反共振の帯域(310〜1070Hz)に裏声が近づくことと矛盾しない。ただし、額の振動が前頭洞に届いた振動であることを示すものではない。

**実装上の落とし穴と対策**

| 問題 | 対策 |
|---|---|
| スマホのスピーカーは低音が弱い(100Hzでは1kHzより40〜50dB低いとの記述あり) | 倍音を含む音を鳴らす(M0で確認済み) |
| 基準音がマイクに回り込み、ハミングと混ざる | 既定は「聞く→ハミング」の交互方式 |
| iOSではマイク使用中に音量が下がる、受話口から鳴るとの報告がある | iOS 27 の実機では発生せず(M0) |
| 1オクターブずれて合わせてしまう | M0で10試行中1回発生。ずれを言葉で伝え、保存するのは実測の周波数にする |
| 大きな声ほど強く震える | 音量メーターで揃えるよう促し、実測の音量も保存して比較時に確認 |
| 期待で評価が偏る | おまかせ探索ではHzを隠し、順番をランダムにする |
| 日によって結果が変わる | 登録のたびに履歴を残し、前回との差を表示。鼻の通りも同時に記録 |
| 無理な発声 | 楽に出せる範囲を基本にし、裏声は任意で案内する。めまいや耳の痛みが出たら中止 |

**追加の調査(2026-11-08、[01-hum-mechanics.md](01-hum-mechanics.md)):** 震え方は高さだけでなく、口や舌の構えでも変わる。唇を閉じると口腔が枝管になり、約1000Hzの音を吸い取る。舌で奥を閉じるとこの谷が高い周波数へ移る。体感の場所からは、どの副鼻腔の空気が動いたかを判定できない。そこで目標を「特定の副鼻腔を狙う」から、「楽な構えで鼻腔に十分な振動を起こし、幅広い周波数を通る」へ変えた(D-030)。管のモデルの計算では、鼻孔を狭めるか、つまんで口を小さく開けると、上顎洞の開口部の圧が低い声で約4倍になった。「ん」の種類とつまむ位置の差は小さかった。

### R-8 環境データ
| 項目 | 結果(2026-11-03に実際のAPIで確認) | 判断 |
|---|---|---|
| 気温・湿度・気圧 | Open-Meteo: キー不要、ブラウザから取得可、過去92日分あり。`jma_seamless`の気圧は約13%欠損 | M3で採用。欠損はモデルの比較で対処 |
| PM2.5 | 取得可だが、日本では約45km格子の予報ベース | 採用するが粗いことを明示 |
| 花粉(Open-Meteo) | 東京で全欠損(欧州限定) | 使えない |
| 花粉(ウェザーニューズ公開データ) | 市区町村別・毎時のCSV、ブラウザから取得可。**2026年10月は404**。2026年は1月中旬〜7月頃の予定 | 使うならシーズン中のみ |
| 花粉(Google) | スギ・ヒノキ・イネ科の予報のみ、過去データなし、課金設定が必要 | 不採用 |

今から数週間の利用なら、**花粉は取得できず、取得できても変動がないので分析できない**。秋の雑草花粉を継続的に取れる供給元も見つからなかった。

また、屋外の気象データは寝室の状態を表さない。短期なら、室内湿度の手入力や「乾燥」タグの方が効く可能性がある。

### R-9 通知
定時通知の手段を比較した。

| 方式 | 評価 |
|---|---|
| Web Push + 小さなサーバー | **推奨。** Cloudflare Workers の定期実行なら維持費はほぼ不要で、削除も容易。iOSはホーム画面への追加が必須 |
| Notification Triggers API | サーバー不要の仕組みだが、Chromeの公式ページで「未リリース」のまま。使わない |
| カレンダー(.ics)やショートカットの自動化 | サーバー不要の代替策 |

「実施済みなら通知しない」を実現するには、完了フラグをサーバーに送る必要がある(HC-5の例外)。

### R-10 スマートウォッチ
HealthKitとHealth ConnectはWebから直接読めない(Health Connectは公式文書では未確認)。主な経路は次のとおり。

| 機器 | 経路 | 備考 |
|---|---|---|
| Apple Watch | ヘルスケアの書き出しファイルを読み込む、ショートカット、Health Auto Export(有料) | 実機で要検証 |
| Android系 | Health Connectはネイティブ前提 | ラッパーか書き出しアプリが必要 |
| Fitbit | **旧Web APIは2026年11月2日に停止予定とされていた**(ページの版によっては10月30日)。後継のGoogle Health APIは審査のある権限 | 個人利用の可否は要確認 |
| Oura / Withings | 個人でも使いやすいとの二次情報あり | 要確認 |
| Garmin | 審査制 | 個人利用は困難な可能性 |

**提案:** M2では朝の手入力のみ。睡眠データは端末に蓄積されるため、連携は後からでも間に合う。

もう1つ重要な点として、**鼻づまりが睡眠を悪化させる逆方向の因果**がある。「前夜の睡眠→翌日の症状」と「当日の症状→その夜の睡眠」の両方を並べて表示する。

### R-11 ストレスの入力欄がない
差別化の要素に挙げられているのに、機能一覧に入力欄がない。夜に0〜10で1タップ入力する欄を追加する。睡眠と同様に逆方向の因果があるので、同じ扱いにする。

**採用を推奨**

### 6.4 ハミング支援(単体で完結するモジュール)

画面上の名称は「副鼻腔振動計」とする(D-016)。

**3つのモード**

- **響きを登録:** 部位を選び、響く音を見つけて登録する
- **今日のハミング:** 登録した音を順にガイドする。毎日のルーティンはここで行う
- **タイマーのみ:** マイク不要。人前や声を出しにくい日に使う

登録は必須にしない。感覚の鋭いユーザーは細かく登録でき、そうでなければ楽な高さの1音だけで「今日のハミング」を始められる。

**響きの登録の流れ**

```
1. 部位を選ぶ   顔の図で位置を案内する
                頬=上顎洞、目の間=篩骨洞、額=前頭洞、鼻の奥=蝶形骨洞
2. 音を探す     自分で: 声をゆっくり上下させ、響いたところで「ここ」を押す(Hzを表示)
                おまかせ: 基準音を順に鳴らす。合わせてハミングし、響きを3段階で選ぶ(Hzは隠す)
3. 確かめる     見つけた音を鳴らしてもう一度ハミングする。半音単位で調整し、響きを1〜3で評価する
4. 登録         「額が響く音 330Hz(E4)」のように保存する。同じ部位に複数登録できる
```

**今日のハミングの流れ**

選んだメニューを「吸いながら基準音を聞く→ハミング(ズレを表示)→休憩」の拍に展開して回す。終わると実施が記録され、直後に2タップの評価を聞く。

**ハミングのメニュー(D-031)**

エアロバイクの規定モードのように、内容の決まったメニューと、自分で組み立てるメニューを選べる。メニューは「ブロック」の並びで、ブロックごとに鼻の構え、高さ、回数、繰り返し、休憩を決める。

| メニュー | 内容 | 狙い(docs/01-hum-mechanics.md) |
|---|---|---|
| いつもの | 今日の音を順に。回数と休憩は設定どおり | これまでの短セット |
| 連続型 | 1分に18回のペースで続ける | これまでの連続型 |
| 山道 | 1回ごとに高さが上がり、また下がる(楽な高さの−3〜+4半音) | 共振の近くを通る(§9.4) |
| スロープ | 1回の「んー」の中で高さを上下に滑らせる | 同上。目標の高さが動き、ズレもそれに対して表示する |
| だんだん強く | 鼻を開ける → 軽く狭める → つまむ | 鼻の出口を変えて、開口部の圧を段階的に上げる(§9.2) |
| インターバル | つまむ「んー」と流す「んー」を交互に4回、3分休んで3セット | 圧を上げる時間と、ガスを運ぶ時間を交互にする(§9.4、U-18) |
| 構えくらべ | 3つの構えを無作為の順に3回ずつ。終わるごとに震えを3段階で答える | 構えの体感を比べる(U-15)。音量も記録し、鼻の横に当てて測ることもできる(U-17) |
| 自分のメニュー | 最大10個。ブロックは最大12個。規定のメニューを元に作れる | 自分の型を作る |

- 高さは楽な高さからの半音で決め、声域の外には出さない。「今日の音」は登録した音(なければ楽な高さ)。
- つまむ「んー」のあとには、展開の段階で必ず「鼻を離して吸う」と「鼻を開けて流す『んー』」を入れる。テストで確かめる(D-035)。
- 狭める、つまむを含むメニューを初めて始めるときに、鼻の構えの説明を1回だけ出す。以後は情報ページとメニューの詳細から開ける。
- 比較実験の日は、比べる音が変わらないよう「いつもの」で行う。
- 構えくらべの順番は日ごとに決まり、ホームと実行画面で一致する(途中からの再開のため)。

**部位の扱い**

副鼻腔ごとに固有の反共振があり、個人差と左右差も大きいという報告があるので(Dang & Honda)、響く音が部位ごとに分かれる可能性はある。ただし、体感の場所がどの副鼻腔に空気の振動が届いたかを示すという検証は見つからなかった。頭蓋骨を伝わる振動も混ざるはずである。

そこで図では副鼻腔の位置を案内するが、登録は「額が響く音」のように体感の言葉で残し、「前頭洞に効く音」とは表示しない。

**誘導の原則**

- 1画面に1指示。「聞く」「ハミング」「評価」で画面全体を切り替え、説明を読まなくても次にすることがわかるようにする
- 初回だけ30秒の練習を入れる(口を閉じて「んー」と出し、響きを確かめる。スマホの置き方も案内する)
- ハミング中は基準音とのズレだけを大きく表示する。今日のハミングでは、流れる帯で先の高さと自分の声の跡を見せ、帯の中心に追う目印の丸を重ねる。滑らせる形は、セットの頭のお手本で音と丸でなぞって聞かせる(D-038, D-039)
- 額を選んだときは、裏声も試すよう短く案内する(暫定)
- 途中で止めても再開できる

**数字から分かったこと**

- **音程合わせの精度:** オクターブずれを除く9試行で、基準音とのズレは中央値9セント、最大22セント。許容幅の50セントに十分収まる。ただし98Hzでは、許容幅に収まっていた時間が61%に下がった。
- **オクターブずれ:** 10試行中1回、261.6Hzの基準音に対して130.8Hz(ちょうど1オクターブ下)で合わせた。実測の周波数を保存する設計なので、データは130.8Hzの評価として使える。
- **音量の余裕:** ハミングは−42〜−52dB、周囲の雑音は−62dB前後。音量の下限(−54dB)と最も低い声の差が2dBしかないので、下限を−60dBに下げる。雑音は周期性の判定で除外できる。
- **声域の測り方:** 「一番高い音」は367Hzと195Hzで大きく変わった。聞き方が曖昧なので、楽な高さと最低音を基準にし、裏声は任意で別に測る。349Hzの震え0は「鼻の奥」について聞いた評価で、額など他の部位には当てはまらない。
- **部位の評価:** 185Hzは「鼻の奥」と「頬」に分かれた。試行数は少ないが、毎回の部位選択は手間の割に安定しない可能性がある。
- **未解明の点:** 基準音の再生中、マイク入力は−62dBで雑音と変わらず、音程も検出されなかった。iOS側でエコー除去が働いている可能性と、マイクの起動直後である可能性がある(設定値は `echoCancellation: false`)。交互方式では録音と再生が重ならないので影響しない。ノイズ抑制と自動音量調整は設定値が返らず、無効になったかは確認できていない。

## 7. 分析設計

### なぜ素朴な相関ではだめか

以下は、**実際には無関係な2系列**を作り、5%水準で「有意」と出る割合をシミュレーションした結果である。

| 条件 | 素の相関 | 差分をとった後 |
|---|---|---|
| 28日、前日との連動なし | 4.9% | 10.0% |
| 28日、前日との連動 0.7 | 21.6% | 5.7% |
| 28日、前日との連動 0.9 | 38.0% | 5.1% |
| **28日、症状が自然に回復しケアの実施率が上がる** | **79.9%** | 7.6% |
| **56日、同上** | **96.2%** | 7.4% |

この回復パターンは、本アプリの利用状況そのものである。放っておいても治る時期に、ハミングが上達すれば「ハミングが効いた」と出てしまう。

差分も万能ではなく、連動のない系列では誤検出が増える(上表の10.0%)。よって、差分のみに頼らず並べ替え検定を併用する。

**他の問題点**

- **検出力:** 有意になるのに必要な相関の強さは、14日で0.53、28日で0.37、56日で0.26。短期では強い関連しか検出できない。
- **多重比較:** 症状5×要因12×時間差4=240通りを調べると、関係がなくても約12件ヒットする。
- **逆の因果:** 調子が悪い日ほど洗浄を増やす、鼻づまりで眠れないなど。
- **同時開始:** 洗浄、ハミング、薬を同時に始めると、何が効いたか区別できない。

### 分析の4段階(提案)

| 段階 | 手法 | 条件 | 表示 |
|---|---|---|---|
| 1 | タイムラインでの目視 | 常時 | 推移と出来事 |
| 2 | 悪化日と非悪化日の比較(症例交差法に近い考え方) | 悪化日が3回以上 | 「候補」と件数 |
| 3 | 時間差付き順位相関 + ブロック並べ替え検定 | 28日以上、仮説メモの要因のみ | 「候補」と強さの目安 |
| 4 | 自己実験(3日ブロックをランダムに割り当て、各ブロック初日は除外) | ハミングなど薬以外 | 「この条件では差あり/差は検出できず」 |

**慢性期の利点:** 状態が比較的安定している慢性期は、急性期より自己実験に向いている。回復傾向の影響は小さくなるが、ゼロとは見なさない。

**開始の順序:** ハミングの開始は遅らせない。比較の基準には、ハミングをしなかった日の「翌朝の1問」と、次の実験を使う。

**最初に確かめる仮説:** 「登録した音で行うハミングは、普段の音程より翌朝の鼻の通りを改善するか」。3日ブロックをランダムに割り当てる。音程の違いは体感でわかるので盲検にはならない。

**自己実験の限界:** 検出できるのは大きな差だけである。Abishek 2019 程度の小さな差なら、数週間の自己実験では「差は検出できず」となる可能性が高い。これは「効かない」という意味ではないので、結果の文言でも区別する。

### 理由コード

| コード | 意味 |
|---|---|
| `INSUFFICIENT_DAYS` | 日数不足 |
| `TOO_FEW_FLARES` | 悪化日が少なすぎる |
| `NO_VARIANCE` | 要因がほとんど変動していない |
| `NO_DATA_SOURCE` | シーズン外などでデータがない |
| `TREND_DOMINATED` | 回復傾向の影響が大きく判別できない |
| `CONCURRENT_CHANGE` | 同時期に薬や手順が変わった |
| `TOO_MANY_MISSING` | 欠損が多い |

## 8. 技術方針(暫定・変更容易)

| 領域 | 案 |
|---|---|
| フロント | Vite + TypeScript + Preact。Service Worker は依存を増やさないよう自作 |
| 保存 | IndexedDB を薄く包んだ追記型イベントログ。使えない環境ではメモリに切り替えて画面に示す |
| ホスティング | GitHub Pages(静的、健康データなし)。無料プランでは公開リポジトリが前提。Actions がテストとビルドを行い、`gh-pages` ブランチに置いたものを「Deploy from a branch」で配信する(D-029) |
| 開発中の実機確認 | cloudflared の一時トンネル。URLが毎回変わるのでテストデータのみ |
| 保存の名前 | `ユーザー名.github.io` は同じアカウントの他の Pages とオリジンを共有するので、DB名とキャッシュ名に接頭辞を付ける |
| 初回の公開 | コミットの作者メールが公開されるので、GitHub の noreply アドレスにした最初のコミット1つにまとめた(D-029) |
| 通知 | Cloudflare Workers の定期実行 + Web Push。購読情報と予定のみ保持 |
| テスト | Vitest。分析、ストリーク、卒業判定、危険サインの優先度は純粋関数に |
| 定数 | ハミングの閾値は `src/modules/hum/rules.ts`、アプリ名は `.env` に集約 |

```ts
type LogEvent = {
  id: string;
  ts: string;   // 時差付き ISO 8601
  day: string;  // 論理日(午前4時区切り)
  kind: 'routine' | 'symptom' | 'tag' | 'med' | 'visit' | 'hum_search' | 'hum_session' | 'hum_morning' | 'sleep' | 'env' | 'protocol' | 'experiment';
  payload: unknown;
  source: 'live' | 'backfill' | 'import' | 'same_as_yesterday';
  v: number;    // スキーマ版
};
```

追記型にする理由は、手順の変更や遡り入力をそのまま履歴に残せ、指標の定義が変わっても再計算でき、書き出しも単純になるため。

### モジュール構成(HC-8)

1つのPWAの中で、ハミングを独立したモジュールとして分ける。別アプリにしないのは、後から日々の記録を足すときに再インストールやデータ移行を不要にするため。

```
src/
  platform/    保存、イベントログ、書き出し、PWA基盤
  modules/
    hum/       基準音、ピッチ検出、探索、練習、効果記録
    daily/     ルーチン、症状、ストリーク、通知設定
    factors/   環境、睡眠、悪化要因の分析
  shell/       有効なモジュールの切り替え
```

| 規則 | 内容 |
|---|---|
| 依存の向き | `hum` が依存するのは `platform` のみ。他のモジュールと `shell` を参照しない |
| 初期状態 | 有効なのは `hum` だけ。起動するとすぐハミング画面を開く |
| 連携 | `daily` から `hum` への片方向のみ。`daily` を有効にすると、イベントログの記録を読んで「ハミング」のチェックを自動で付ける |
| 効果の指標 | 前後評価と翌朝の1問の記録は `hum` の形式で持つ。`daily` を使うときは朝の確認の中で同じ形式で記録し、同じ質問を重複させない(D-023) |
| 縮退動作 | マイクが使えなくても基準音とタイマーは動く。通信は不要 |
| 書き出しと削除 | モジュール単位で可能 |

## 9. マイルストーン

**原則(提案):** 動機であり技術リスクも最大のハミングから作る。他の機能は使いたくなってから足す。

後から取得できるかどうかは、順序を決めるうえで次のように効く。

| データ | 後から取得 | 扱い |
|---|---|---|
| 症状、ケア実施、タグ、薬 | **不可** | ハミング単体の間は「翌朝の1問」で代替。本格的に記録したくなった時点でM2を入れる |
| 気温、湿度、気圧 | 過去92日分は可能(確認済み) | M3で十分 |
| PM2.5 | 過去分を取得可能(30日分を確認済み) | M3で十分 |
| 睡眠(ウォッチ) | 端末に蓄積(機種次第) | M3で十分 |

| M | 内容 | 完了条件 |
|---|---|---|
| **M0(完了)** | 実機検証(§6.4) | 基準音とマイクの方式が確定 |
| **M1 ハミング単体(実機で使用確認済み)** | 声域測定、基準音、チューナー、部位の案内と響きの登録、今日のハミング、前後評価、翌朝の1問、中止条件と危険サイン、JSON書き出し、GitHub Pagesへの公開 | 他の機能がなくても毎日使える |
| **M1.5 比較実験(実装済み、実機確認待ち)** | 登録した音と普段の音程の比較 | 割り当てから結果表示まで自動で完了 |
| **M2 日々の記録と通知(通知サーバー以外を実装済み、実機確認待ち)** | ルーチン、症状、タグ、薬、ストリーク、卒業カウンター、タイムライン、受診サマリ、週次評価、嗅覚チェック、カレンダー用の書き出し。**未着手:** Web Push(D-021)。地点登録はM3へ移した | 毎日1分以内で記録でき、通知が設定どおり届く |

## 11. 検証の状況

**実際に確認した(2026-11-03)**

- Open-Meteo の気象とPM2.5: ブラウザ相当の Origin 付きで取得でき、CORS は `*`。過去92日分を取得できた。`jma_seamless` の気圧は2232点中1935点のみ。
- Open-Meteo の花粉: 東京でイネ科、ヨモギ、ブタクサはすべて欠損。
- ウェザーニューズの花粉: 2025年3月は毎時のCSVを取得でき、CORSは `*`。2026年10月は404。
- §7 の数値: 独自のシミュレーション(各4000回)。正規分布の仮定による概算値。
- Pruthi 2004 の本文: 約300Hzの第1共鳴(Fujimura の引用)と、鼻腔や副鼻腔の形による個人差の記述。
- AAFP 2017 の本文: 第一選択、抗菌薬の位置づけ、紹介基準、CTと内視鏡の記述。
- iPhone 12 mini / iOS 27 での基準音、マイク、ホーム画面起動、消音スイッチ(2026-11-04、§6.4)。1台で各1回の結果で、他の機種には当てはまらない場合がある。
- M1の全画面の流れ(合成マイク、Chromium、幅375px)と、サーバー停止時のオフライン起動。iPhoneでの使用はユーザーが確認(2026-11-04)。
- M1.5とM2の画面(合成マイクと試験データ、Chromium、幅375px、ライトとダーク)。iPhoneでの確認はこれから。カレンダー用ファイルの取り込み、受診サマリと記録の書き出しは、iPhoneでは未確認。
- タブとカード型の新しい見た目(2026-11-06、試験データ、Chromium、幅375px、ライトとダーク)。ハミングだけの3タブと、日々の記録を使う4タブの両方。iPhoneでの確認はこれから。
- 端末の戻る操作(2026-11-09、合成マイク、Chromium、幅375px)。メニューの詳細から一覧、ホームへ1画面ずつ戻り、履歴が増え続けないこと、ハミング中の戻るで質問へ進み、質問での戻るで答えた分だけ記録されることを確かめた。左端のスワイプは合成したタッチ操作で確かめた。iPhone のホーム画面アプリでの確認はこれから(同じ日にユーザーが iPhone で試したのは、この変更を含まない公開版だった)。
- アプリのアイコン(2026-11-09)。書き出した PNG を Pillow で読めることと、同じ形の SVG を Chromium で描いた画像とほぼ一致すること(512px で8段階を超えて違うのは輪郭の200画素、最大36段階)を確かめた。iPhone のホーム画面での見た目はこれから。
- 流れる帯(2026-11-11、合成マイク、Chromium、幅375px、ライトとダーク)。スロープ、山道、つまむ構えを含む自分のメニューで、帯が先から流れてくること、声の跡、回ごとの判定とセットの丸、終わりの判定の数を確かめた。合成マイクは帯の真上を歌うので、GREAT 以外の判定と、実際の声で追いやすいかは未確認。iPhoneでの確認はこれから。
- お手本と広げた帯(2026-11-11、合成マイク、Chromium、幅375px、ライトとダーク)。スロープの始めと休憩のあとにお手本が入り、点線の帯の上を丸がなぞって細い跡を残すこと、上と下の帯が1つの形につながること、ハミング中の音のない丸、休憩明けのセットの丸を確かめた。お手本の音は Web Audio に予定された高さと時刻が帯の中心と一致することを確かめたが、耳での確認と iPhone での確認はこれから。タイマーだけのときにお手本を飛ばすことと、お手本の「次へ進む」はテストで確かめた。
- ハミングのメニュー(2026-11-08、合成マイク、Chromium、幅375px)。だんだん強く、構えくらべ(鼻の横に当てる設定を含む)、スロープ、自分のメニューを最後まで実行し、記録の中身を確かめた。iPhoneでの確認、特に鼻の横に当てたときの音量の再現性はこれから。

**二次情報にとどまるもの**

- NICE NG79の基準は GPnotebook 経由。EPOS 2020 の原文は未確認。
- 症状の0〜3、3〜7、7〜10の区分は EPOS 2012 系の資料に基づく。
- Oura、Withings、Garmin の条件はブログなどの二次情報。
- Maniscalco 2003 の内容は検索結果の要約と学位論文の要旨から確認。本文は取得不可(403)。Granqvist 2006 は要旨のみで、数値なし。
- 悪臭や片側症状の扱いは英国の地域ガイドラインの例であり、日本の診療基準ではない。
- 片側の上顎洞炎に占める歯性の割合(最大75%)はナラティブレビュー内の1つの引用で、同論文も報告の不一致を認めている。
- スマホスピーカーの低音特性は特許文献の記述で、特定の機種の実測ではない。
- iOSのマイク使用中の音量低下は古い不具合報告が中心で、iOS 27 の実機では発生しなかった。

**原典確認で修正した点**

- Abishek 2019 は本文で確認した。群間差の約3.4点は12週時点の平均値の差から筆者が計算したもので、論文には記載がない。著者自身も、少人数、追跡期間の短さ、遵守状況を測定していない点を限界に挙げている。
- 初稿にあった「自己評価の嗅覚は検査と相関が弱い」「基本情報が揃った紹介状は22%」は、原典を特定できなかったため削除した。
